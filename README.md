# Omeka-S-module-IiifManifestDerivatives

IIIF Manifest Derivatives is an Omeka S module that extends the manifests generated by the IIIF Server module.

By default, the IIIF Server module generates Presentation 3 manifests using the image derivatives stored locally by Omeka S (such as square, medium, and large).

In some deployments, however, Omeka S is intentionally kept lightweight and does not serve images directly. Instead, all image delivery is delegated to a dedicated IIIF Image API server, which is responsible for generating tiles and derivatives on demand.

In this architecture:

- Omeka S stores only the original metadata and media records;
- image processing and delivery are handled by an external IIIF Image API server;
- local Omeka image derivatives are unnecessary and should not be referenced in IIIF manifests.

The module listens to the iiifserver.manifest event and enriches the generated IIIF Presentation 3 manifest by:

- adding a manifest thumbnail;
- adding thumbnails to every canvas;
- replacing annotation bodies with IIIF Image API resources;
- adding image dimensions (width and height) to canvases and image bodies.

The image URLs are generated using the value of the resource's dcterms:identifier (or dc:identifier) and the IIIF Image API configuration already defined in the IIIF Server module.

## Requirements

- Omeka S (^4.2.0)
- IIIF Server module
- A configured IIIF Image API endpoint

## Installation

Install the module like any standard Omeka S module:

Download or clone the module into the modules directory.
Rename the directory to:
IiifManifestDerivatives
Enable the module from the Omeka S administration interface.

No additional configuration is required.

## How it works

When IIIF Server generates a Presentation 3 manifest for an Item, this module intercepts the manifest before it is returned and updates it.

### The module:

1. reads the item's dcterms:identifier (fallback: dc:identifier);
2. reads the IIIF Server settings:
    - iiifserver_media_api_url
    - iiifserver_media_api_default_version
3. constructs the corresponding IIIF Image API URLs;
4. extracts image dimensions from the first media containing width and height metadata;
5. injects the following information into the manifest.


### Manifest

Adds:

```
"thumbnail": [
  {
    "id": ".../square/200,200/0/default.jpg",
    "type": "Image",
    "service": [...]
  }
]
```

### Canvases

Each canvas receives:

- thumbnail
- width
- height


### Annotation bodies

Each annotation body is replaced with an Image API resource similar to:

```
{
  "id": ".../full/max/0/default.jpg",
  "type": "Image",
  "format": "image/jpeg",
  "width": 6000,
  "height": 4000,
  "service": [
    {
      "id": "...",
      "type": "ImageService3",
      "profile": "level2"
    }
  ]
}
```

### Identifier

The module expects every Item to contain one of the following properties:

- dcterms:identifier
- dc:identifier

The identifier must correspond to the identifier used by the IIIF Image API server.

> If no identifier is found, the manifest is left unchanged.

### Image dimensions

The module retrieves image dimensions from the first media attached to the item.

It searches in:

- mediaData()
- ingestionData()

If no dimensions are available, width and height remain 0.

## Notes

The module only modifies manifests generated for Items.
Other Omeka S resources are ignored.
All IIIF Image API URLs are generated using the configuration already defined in the IIIF Server module, so no duplicate configuration is necessary.
